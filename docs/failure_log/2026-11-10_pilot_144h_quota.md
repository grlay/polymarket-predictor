# Failure log: first unattended pilot cutoff (144 h), 2026-11-10

Status: written 2026-11-10 14:45-15:xx HKT from the VM log and a read-only DB query. Items marked UNKNOWN are not yet established; fill them in before the report uses this entry.

## What was planned
Cron fires at 05:00 UTC (13:00 HKT) with cutoff 2026-11-10T04:59:00Z: build the snapshots, then run the 8 systems for two markets (Rubio `6723099`, blockade `6282802`) on `gemini-3.6-flash`. Two retry passes follow at 05:06 and 05:11 UTC. The window (`llm.max_forecast_delay_seconds`) is 900 s and closes at 05:14 UTC. After that a snapshot is skipped for good; the rule is never bent and no other model is substituted.

## What happened (evidence: `artifacts/research/pilot_cutoff.log` on the VM, DB query, VM `date -u` = 06:45:50 UTC)
- Pass 1: 23 calls, 2 cache hits, 6,939 prompt and 2,095 completion tokens. One snapshot (`70ca060b5ad0c2858164bc1087cbb103b66d693cb0d3a115155e2e85dd63dfa3`) failed with `HTTP 429: You exceeded your current quota`.
- Passes 2 and 3: 7 calls each, 0 tokens, the same 429 on the same snapshot. The retries ran on the same model, as designed, and the quota stayed exhausted.
- Result in the database for cutoff 2026-11-10T04:59Z: 8 rows for Rubio (all `ok`, horizon 144.0 h, model `gemini-3.6-flash`, all generated 283 s after the cutoff, inside the window); 0 rows for blockade.
- Outcome: 8 of 16 expected forecasts. The blockade 144 h forecast does not exist and cannot be created without breaking the 900 s rule. It is reported as a missed snapshot, like the 168 h cutoff on 2026-11-09 (Gemini access not ready).

## Cause
- Direct cause: provider quota error (HTTP 429).
- The log line is truncated at "Quota exceed" because `src/agents/llm_client.py` keeps only the first 300 bytes of the error body, so the quota name was never recorded.
- AI Studio rate-limit page (user's screenshot, 2026-11-10 afternoon HKT) lists for Gemini 3.6 Flash: 5 / 250K / 20 (columns not labelled in the screenshot; read as requests per minute, tokens per minute, requests per day). Gemini 3 Flash shows the same; Gemini 3.1 Flash Lite shows 15 / 250K / 500. These are free-tier-sized limits; the key's tier is still to be confirmed on the page.
- AI Studio pages (user's screenshots, same afternoon): the project "Default Gemini Project" is on the **Free tier**; the columns are RPM / TPM / RPD. Peak usage over 28 days for Gemini 3.6 Flash: **9 / 5 RPM and 24 / 20 RPD** (both over the limit, shown in red), tokens 13.35K / 250K (not a constraint). The banner reads "You have reached a rate limit. Set up billing...". The usage chart shows two days of activity with about 30 errors of type 429 plus some 503 and 400.
- Cause (supported by the above, still an inference about which of the two limits produced the first 429): the free-tier cap of 20 requests per day, which is below the roughly 27 requests (23 calls plus about 4 cache hits) one two-market cutoff needs. Evidence it was the daily and not the per-minute limit: the two retry passes at 05:06 and 05:11 UTC were refused with 0 tokens, and a per-minute limit would have recovered within a minute.
- Why the 2026-11-09 dry run was not refused: the page's day is UTC-8 (Pacific), so it ends at 08:00 UTC. The dry run (about 07:59 UTC on 11-09) fell in the previous day, so it did not share a quota day with the 2026-11-10 05:00 UTC cutoff. The counter also appears to allow a small overshoot (24 against 20 is shown), which is why 23 calls passed. (Reading of the page, not verified against documentation.)
- Contributing design facts: all calls go through one key and one model; retries stay on the same model by design; the retry passes cannot help against a quota that does not reset within the 900 s window.

## Why the response was not "run it late" or "switch model"
A late forecast would be generated after information the cutoff excludes, and a model switch would mix models inside the daily series. A visible gap is a cleaner and reportable result than a repaired one. Nothing was re-run by hand.

## Consequences for the analysis
- Blockade has no 144 h point; every scoring or plot must say so rather than interpolate.
- All cutoffs are reported and none selected afterwards (existing rule).
- The pilot is a pipeline demonstration; this entry is evidence about operational reliability, not about forecast quality.

## Decision and fix
UNKNOWN until the quota type is known. Options to be decided by the user and logged in `docs/decisions_log.md` before the 2026-11-11 cutoff (13:00 HKT): raise the quota (billing/tier), space or reduce the calls, or accept further gaps. No config or code has been changed.

## Lessons for the report
1. A single-key, single-model design has a single point of failure; the retry design does not cover a quota that outlasts the window.
2. Rate limits were not recorded before the first unattended run (a known open item).
3. A successful dry run did not predict this failure because it fell in a different quota day. Quota days follow Pacific time (08:00 UTC boundary), so a test just before the boundary does not show what the cutoff will meet. The limits of the tier should have been compared with the requests a cutoff needs (about 27 against 20 per day) before the first unattended run.
